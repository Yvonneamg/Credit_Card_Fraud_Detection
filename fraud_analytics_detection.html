Credit Card Fraud Detection¶

Business Problem¶

Financial institutions need to identify potentially fraudulent transactions while minimizing the number of legitimate transactions incorrectly flagged for investigation.

This project analyzes credit card transactions to:

  1. Understand the characteristics of fraudulent transactions.
  2. Identify transaction-level patterns associated with fraud.
  3. Investigate whether transaction timing and transaction value are associated with higher fraud risk.
  4. Use SQL to answer targeted business questions.
  5. Apply Isolation Forest to identify anomalous transactions.
  6. Evaluate how well detected anomalies align with known fraudulent transactions.
  7. Translate analytical findings into practical fraud-monitoring recommendations.

Analytical Approach¶

The analysis combines:

  • Python for data preparation, exploratory analysis and anomaly detection.
  • SQL / SQLite for targeted transaction analysis.
  • Statistical analysis to compare fraudulent and legitimate transactions.
  • Isolation Forest for unsupervised anomaly detection.

This project analyzes the Kaggle Credit Card Fraud Detection dataset to identify fraudulent transactions using SQLite, pandas and machine learning in Python.

1. Data Loading¶

The dataset contains 284,807 credit card transactions made over approximately two days.

The available variables include:

  • Time: seconds elapsed since the first transaction.
  • V1–V28: anonymized transaction features.
  • Amount: transaction amount.
  • Class: target variable where 0 represents legitimate transactions and 1 represents fraud.

Class Distribution¶

The dataset is highly imbalanced, with Fraudulent transactions representing only 0.1667% of the cleaned dataset, while 99.8333% are legitimate transactions.

This imbalance is important for fraud detection because a model can achieve very high accuracy simply by classifying most transactions as legitimate.

Therefore, model performance will be evaluated primarily using:

  • Precision
  • Recall
  • F1-score

rather than accuracy alone.

Threshold Selection¶

Rather than relying solely on a mean + 2 standard deviation threshold, I use the 95th percentile of hourly transaction volume to identify unusually high activity.

This approach is appropriate because it does not require transaction volume to follow a normal distribution and provides an intuitive business interpretation: the highest 5% of hourly periods are considered unusually active.

A percentile-based threshold is also less sensitive to extreme observations than a mean-based threshold, making it useful for identifying unusually high transaction activity in potentially skewed transaction-volume data.

Therefore, an hourly period is classified as Unusually High when its transaction volume exceeds the 95th percentile of observed hourly transaction volume.

Isolation Forest — Anomaly Detection¶

Objective¶

The previous exploratory analyses identified several transaction characteristics that may be associated with fraudulent activity.

The next step is to determine whether these characteristics can be combined to identify transactions that appear unusual relative to the wider transaction population.

For this purpose, I use Isolation Forest, an unsupervised anomaly detection algorithm.

The model is trained using 31 transaction-level features across 283,726 observations. These features include the anonymized V1–V28 variables together with the engineered variables Log_Amount, Hour and Is_Early_Morning.

The objective is not to classify fraud directly, but to identify transactions with unusual characteristics and then assess how well those anomalies correspond to known fraudulent transactions.

Business objective¶

From a business perspective, the goal is to determine whether anomaly detection can help prioritize potentially suspicious transactions for further investigation.

Feature Selection¶

The model uses 31 features.

These consist of:

  • V1–V28: the 28 anonymized numerical transaction features in the original dataset.
  • Log_Amount: a logarithmic transformation of transaction amount.
  • Hour: the transaction hour derived from transaction time.
  • Is_Early_Morning: an indicator identifying transactions occurring between midnight and 5:00 AM.

The feature set therefore combines the original transaction characteristics with engineered variables motivated by the earlier exploratory analysis.

This allows the anomaly detector to evaluate unusual transaction profiles using both the underlying anonymized features and the business-relevant transaction characteristics.

Training the Isolation Forest¶

Setting the Contamination Parameter¶

The training fraud rate is approximately 0.1667%.

This value is used as the Isolation Forest contamination parameter.

The contamination parameter represents the expected proportion of observations that the algorithm will treat as anomalous.

Therefore, the model is configured with an expected anomaly proportion of approximately 0.167%, corresponding to the observed fraud prevalence in the training data.

Important modeling assumption¶

This does not mean that Isolation Forest is learning which transactions are fraudulent.

Isolation Forest remains an unsupervised anomaly detection algorithm.

Instead, the known training fraud prevalence is being used as a practical assumption about how many observations should be considered anomalous.

The resulting anomaly predictions are then evaluated against the known fraud labels in the unseen test set.

Model Evaluation¶

Evaluating anomaly detection against known fraud¶

Although Isolation Forest is an unsupervised model, this dataset contains known fraud labels.

This allows us to compare the anomaly flags generated by the model against confirmed fraudulent transactions.

Because fraud is highly imbalanced, accuracy is not the primary performance measure.

Instead, the analysis focuses on:

Precision¶

Of all transactions flagged as anomalous, what proportion were actually fraudulent?

This is particularly relevant to the investigation team because low precision could result in a large number of legitimate transactions being sent for review.

Recall¶

Of all confirmed fraudulent transactions, what proportion were successfully flagged?

Recall measures the model's ability to identify fraudulent activity.

F1-score¶

The F1-score provides a balance between precision and recall.

This is useful when both missed fraud and unnecessary investigations have business consequences.

A recall of 21.13% means that the model identified approximately one in five confirmed fraudulent transactions in the test set.

Conversely, approximately 78.87% of confirmed fraud was not detected by the anomaly detector.

This is a significant limitation if the objective is to maximize fraud detection coverage.

Business Interpretation¶

What Does the Model Tell Us?¶

The Isolation Forest successfully identifies a small subset of transactions that are statistically unusual.

However, the test-set results show that unusual transaction behavior does not consistently correspond to confirmed fraud.

The model flagged 146 transactions as anomalous.

Of these:

  • 30 were fraudulent
  • 116 were legitimate

This produces a precision of 20.55%.

At the same time, the model identified only 30 of the 142 fraudulent transactions in the test set, producing a recall of 21.13%.

What this means for the business¶

The model can potentially be used as one signal within a broader fraud-monitoring system, but it should not be used as a standalone fraud decisioning mechanism.

Its strongest potential use is investigation prioritization.

For example, anomaly detection could be combined with:

  • transaction amount,
  • transaction timing,
  • customer transaction history,
  • previous suspicious activity,
  • velocity indicators,
  • and other fraud-risk signals.

A transaction that is anomalous and simultaneously exhibits several other risk indicators could receive a higher investigation priority.

Key conclusion¶

The Isolation Forest provides evidence that some fraudulent transactions exhibit unusual transaction profiles.

However, with a recall of only 21.13%, the model misses the majority of confirmed fraud.

Therefore, the current model should be treated as a baseline anomaly detection approach, rather than a production-ready fraud detection solution.

Business Recommendations¶

Translating the Analysis into Fraud-Monitoring Actions¶

Based on the exploratory analysis and the Isolation Forest results, the following actions are recommended.

1. Use anomaly detection as a supporting signal¶

The Isolation Forest should not be used as a standalone fraud classifier.

Its current recall of 21.13% indicates that the model misses a large proportion of confirmed fraud.

Instead, anomaly detection should be treated as one input into a broader fraud-risk framework.

2. Prioritize flagged transactions for investigation¶

Although the model identifies only a small number of transactions as anomalous, approximately 20.55% of flagged transactions were confirmed as fraud.

This indicates that the anomaly signal contains useful information and could potentially help prioritize manual investigation.

3. Combine anomaly detection with behavioral indicators¶

The next stage should investigate whether anomaly flags become more useful when combined with other risk indicators identified earlier in the analysis.

Potential signals include:

  • transaction amount,
  • transaction timing,
  • early-morning activity,
  • unusual transaction characteristics,
  • and historical transaction behavior.

4. Improve fraud detection coverage¶

The current recall of 21.13% indicates that the majority of confirmed fraud is not captured by the anomaly detector.

Future modeling should therefore investigate supervised classification approaches that can directly learn from the known fraud labels.

Potential approaches include logistic regression, tree-based models and other imbalance-aware classification techniques.

5. Evaluate models using business costs¶

Model selection should not be based solely on statistical metrics.

The business should consider the relative cost of:

  • missing a fraudulent transaction,
  • incorrectly flagging a legitimate transaction,
  • and manually investigating a suspicious transaction.

This would allow the fraud-monitoring threshold to be selected according to business priorities rather than simply maximizing a single metric.

6. Validate using future or temporally separated data¶

Before considering deployment, the approach should be tested against future transactions or a temporally separated validation set.

This would provide a stronger indication of how the fraud-monitoring approach would perform in a real operational environment.
